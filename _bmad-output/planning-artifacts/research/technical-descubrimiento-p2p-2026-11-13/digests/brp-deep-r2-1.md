### Claims — BRP spec details

1. **BRP purpose & shape** {claim}: BRP v0 is a *discovery* protocol: two peers who previously exchanged public keys connect with no other prior info. It is designed for connection-oriented bidirectional transports; the only transport in v0 is Tor v3 hidden services (transport_id `"org.briarproject.bramble.tor"`). {source}: https://code.briarproject.org/briar/briar-spec/-/commit/ee7efa68c6e235609d87fd1fce360242306f7f29 {publisher}: Briar Project GitLab, briar-spec, commit ee7efa68 (akwizgran, 2019) {accessed}: 2026-11-13 {confidence}: high {class}: HECHO

2. **KDF chain (spec v0, verbatim)** {claim}: `raw_secret = X25519-DH(pri, pub)` — must abort if all-zeroes; `static_master_key = HASH("org.briarproject.bramble.transport/STATIC_MASTER_KEY", raw_secret, pub_a, pub_b)`; `rendezvous_key = KDF(static_master_key, "org.briarproject.bramble.rendezvous/RENDEZVOUS_KEY", int_8(protocol_version))`, protocol_version = 0; `stream_key = KDF(rendezvous_key, "org.briarproject.bramble.rendezvous/KEY_MATERIAL", transport_id)`; then `key_material = STREAM(stream_key, 64)` — first 32 bytes = Alice's seed, last 32 = Bob's; each seed is an Ed25519 private key per RFC 8032 §5.1.5 used as the master identity key of a Tor v3 hidden service (address per rend-spec-v3 §6). Each peer publishes its own onion and dials the other's. {source}: https://code.briarproject.org/briar/briar-spec/-/blame/master/protocols/BRP.md + commit d5d6e2a3 {publisher}: Briar GitLab {accessed}: 2026-11-13 {confidence}: high {class}: HECHO

3. **Rendezvous window mechanics** {claim}: each peer keeps endpoints open and dials the peer's onion once per minute for up to 48 h; offline peers reopen endpoints and resume on return; if no connection within 48 h of key exchange, rendezvous fails and must be manually restarted by both. When BRP gets a connection it passes it to the application layer; the app tells BRP when no further rendezvous connections are needed, then BRP closes endpoints. {source}: commit d5d6e2a3 ("Add section on use of rendezvous connections") {accessed}: 2026-11-13 {confidence}: high {class}: HECHO

4. **Data over the connection** {claim}: "BRP does not exchange any data over the underlying transport" — BRP returns the connection plus the static master key to the calling application for use by other protocols. Version negotiation is trivial: version is a constant (0) bound into the KDF label inputs, not negotiated on the wire. {source}: commit 37538637 (MITM discussion diff) + BRP.md blame {confidence}: high {class}: HECHO

5. **Stated purpose = initial rendezvous, not continuous availability** {claim}: BRP is one-shot per contact pairing — it exists to bootstrap the *first* connection after key exchange; the app ends it once ongoing connectivity is established. It is not a persistent-address scheme. {source}: BRP.md §1 + §2.3 as retrieved {confidence}: high {class}: HECHO

6. **Sibling specs** {claim}: BSP is the application-layer delay-tolerant sync protocol (groups, message graphs, devices/peers) that *requires* an underlying transport-layer security protocol providing confidentiality/integrity/authenticity/forward secrecy — i.e., BRP yields the connection, BTP secures it, BSP syncs over it. BHP/BQP handle contact-adding (handshake/QR). {source}: https://code.briarproject.org/briar/briar-spec/-/blame/master/protocols/BSP.md {confidence}: high {class}: HECHO

7. **Briar Mailbox = bilateral "store at my own always-on device"** {claim}: YES — a Mailbox is the *owner's* second device (e.g., spare Android) reachable via Tor onion; contacts deposit messages for the owner and pick up messages the owner left for them. API: HTTP+Bearer token, per-contact random 32-byte `token`/`inboxId`/`outboxId`; "Each Mailbox only delivers messages between its owner and their contacts, so no information is exposed to third parties." This is exactly the "deposit records only on direct contacts' infrastructure, encrypted per recipient" pattern — but it requires a second always-on device per user, not the mutual-relay model under study. {sources}: https://github.com/briar/briar-mailbox (README + API.md), https://www.briarproject.org/news/2023-briar-mailbox-released/ {publisher}: Briar Project, 2023 {confidence}: high {class}: HECHO

### Claims — rotation feasibility

8. **Höller et al. WTMC 2021** {claim}: measured end-to-end provisioning (create → reachable) of v3 onion services; descriptor upload dominates; a fresh v3 service uploads 16 descriptors initially (4 HSDirs × 2 replicas × 2 time periods). Companion thesis data: v3 default provisioning ≈5 s (vs v2 ≈33 s); an "acceptance threshold" of 6.35 s is cited. Conclusion: dynamic short-lived onion services "are already feasible for peer-to-peer communication in certain scenarios" — feasible at per-contact/per-purpose granularity where ~seconds of provisioning latency is tolerable. {sources}: https://www.mroland.at/publications/2021-hoeller-wtmc/Hoeller_2021_WTMC2021_DynamicOnionServices.pdf ; https://www.jku.at/fileadmin/gruppen/177/Raab_2021_MasterThesis_UnlinkableOnionServices.pdf ; DOI 10.1109/SPW53761.2021.00012 {publisher}: IEEE SPW/WTMC, May 2021 {confidence}: high for ~5 s provisioning & descriptor-upload dominance; medium for the exact per-scenario rotation conclusion (I could not retrieve the paper's final "scenario" table verbatim) {class}: HECHO

9. **What bounds rotation below** {claim}: two independent floors. (a) Provisioning/propagation: tens of seconds → periods must be ≫ 60 s or the service spends a large fraction unreachable and multiplies concurrent intro circuits (meshtor's own rationale, verbatim: "a period short enough to matter for exposure would spend a visible fraction of itself unreachable"). (b) Tor's HSDir epoch: `hsdir-interval` default 1440 min; v3 descriptors are valid for two time periods and republish every 60–120 min — rotating *within* a time period doesn't change HSDir placement but each new service still pays full provisioning. Practically: **hours–days is comfortable; ~minutes is the lower bound; sub-minute breaks.** {sources}: meshtor rotate.rs + https://tpo.pages.torproject.net/core/torspec/rend-spec/deriving-keys.html {confidence}: high {class}: HECHO

10. **meshtor derivation** {claim}: `ROTATION_PERIOD = 86_400` s, `SEED_LEN = 32`; onion address = f(seed, floor(clock/86400)) — confirmed at the design level ("the onion address is derived from that seed and the day"). A rotating host **publishes three consecutive epochs concurrently** (yesterday/today/tomorrow — skew tolerance + not-yet-propagated tomorrow); joiners try the same three. Explicit warnings: rotation ≠ revocation, not forward-secret — anyone holding the seed derives all epochs forever. Non-configurable period (a distinctive period is fingerprintable). {source}: https://0rcus.vercel.app/git/r/meshtor/files/src/rotate.rs + project README {accessed}: 2026-11-13 {confidence}: high for constants & 3-epoch concurrency; the literal KDF expression (which hash → ed25519) was not in retrieved snippets — unverified {class}: HECHO (+1 unverified detail)

11. **Zerion B.4** {claim}: v3 onion rotates every **5–14 days, uniform-randomized**; during the `announcing` phase `onion_current` and `onion_next` run concurrently; peers learn the new onion via an in-band transport-property update over the existing encrypted sync session; old onion retired when all active peers migrated or after 90 days. Concurrent old+new is the established migration pattern — corroborated by meshtor's 3-epoch publish. {sources}: https://github.com/zerionproject/Zerion/blob/0ad92a02/docs/wire/B4_ONIONWRAPPER_API.md ; https://zerion.chat/blog/zerion-1-5-release.html {publisher}: Zerion project, v1.5 (doc dated 2026-05-01) {confidence}: high {class}: HECHO — note Zerion rotates by *announcement* (needs a live channel), meshtor by *derivation* (offline computable); BRP-derived rotation would follow the derivation model.

### Claims — bramble crate fidelity

12. {claim}: `bramble-rendezvous 0.1.0` (rmartinho, CC0-1.0, 2021-10-16, no later releases) **structurally implements BRP v0 faithfully**: same DH → static_master_key → rendezvous_key → stream_key chain, Alice/Bob role by pubkey ordering, 60 s dial interval, 48 h max attempt window, `select!` on listen-vs-connect, returns `(conn, static_master_key)` to caller. **Two fidelity caveats found in source**: (a) the KDF label constants read `org.briarproject.bramble.transport/RENDEZVOUS_KEY` and `.../KEY_MATERIAL`, while spec text shows `org.briarproject.bramble.rendezvous/...` — if accurate, derived keys differ and the crate is **wire-incompatible with Briar**; (b) it is transport-agnostic — the `Rendezvous` trait leaves Ed25519/onion derivation to `prepare_endpoints(stream_key, role)`, and **no Tor transport implementation ships in the workspace** (deps: bramble-{common,crypto,data,handshake,qr,rendezvous,sync,transport} only). {source}: https://docs.rs/bramble-rendezvous/latest/.../src/bramble_rendezvous/protocol.rs.html ; https://crates.io/crates/bramble {confidence}: high on structure; medium on label mismatch (could reflect a spec-text revision I couldn't see — verify against current BRP.md) {class}: HECHO

**Verdict: spec-faithful core, partial overall** (no Tor transport shipped; label-constant discrepancy must be verified before reuse).

### Claims — Tapir

For a Rust codebase it's a design/mechanics reference only (e.g., authenticated-app pattern over a derived onion), not a linkable dependency. {sources}: https://git.openprivacy.ca/cwtch.im/tapir ; https://pkg.go.dev/git.openprivacy.ca/cwtch.im/tapir ; https://openprivacy.ca/discreet-log/04-tapir-and-rust/ {confidence}: high {class}: HECHO
