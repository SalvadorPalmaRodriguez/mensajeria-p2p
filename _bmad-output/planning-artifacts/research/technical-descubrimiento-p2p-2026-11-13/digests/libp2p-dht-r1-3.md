### Claims — libp2p rendezvous

- **Spec status**: Rendezvous spec is a **Working Draft, Lifecycle 1A, "Active", latest revision r3 dated 2021-07-12**; last spec-repo commit touching it is a typo fix (Dec 2022). It has never matured past draft. {github.com/libp2p/specs/blob/master/rendezvous/README.md + commits page, libp2p, accessed 2026-11-13, high, spec}
- **Mechanics**: Peers open a libp2p stream (`/rendezvous/1.0.0`) to a rendezvous point and send `REGISTER` with a namespace + a serialized **signed peer record** (self-registration only — you cannot register third parties). `DISCOVER` takes optional namespace, result limit, and a **cookie** for pagination/incremental refresh. `UNREGISTER` cancels. {spec README, high, spec}
- **TTL**: default 2 h; rendezvous point may bound it, recommended max 72 h; TTL is relative — responses return *remaining* TTL (confirmed in spec issue #330). {spec + github.com/libp2p/specs/issues/330, high, spec}
- **Recommended server limits** (per spec guidance): max namespace length 255 chars, max 1000 registrations/peer, max 1000 peers per query. {deepwiki.com/libp2p/specs/7.3-rendezvous-protocol, medium, spec}
- **What the point learns**: registrant's PeerID + **all multiaddrs in the signed peer record (cleartext)** + namespace; discoverer's PeerID + queried namespaces. A `DISCOVER` **with no namespace returns ALL registrations on the point** — namespaces are not secrets and there is **no access control in the spec**. A libp2p forum thread confirms namespaces are "open by default… freely shares available namespaces with anyone who asks." {spec README + discuss.libp2p.io/t/how-to-build-magic-wormhole-style-authorization/2419, high, spec}
- **No registration authorization exists in rust-libp2p's implementation** — discussion #5638 asked for an auth hook; maintainer response: build a wrapper behaviour (cf. `swarm::behaviour::Toggle`, `libp2p-allow-block-list`), i.e. auth must be added at connection/behaviour level, not inside the protocol. {github.com/libp2p/rust-libp2p/discussions/5638, high, spec}
- **Rendezvous is federated, not decentralized** — libp2p's own docs state it "introduces a single point of failure"; spec assumes **"known rendezvous points"** — the protocol has no mechanism for finding rendezvous points (open spec issue #145 proposes making every node a rendezvous node; unresolved). Any node *can* be a rendezvous point. {libp2p.io/docs/rendezvous + specs issue #145, high, spec}
- **Standalone w.r.t. kad-DHT**: the protocol is a plain stream protocol between two peers; it does not depend on kad-DHT or bootstrap. Canonical use case in docs is discovering **circuit relays** — relays are banned for us; noted, not researched. {spec/docs, high, spec}
- **rust-libp2p**: `libp2p-rendezvous` is **implemented, released, actively maintained** — v0.17.1 (2026-04-02) / v0.18.0 (~Sep 2026 per deps.dev), MIT, ~1.9M downloads, ~127 dependents, owned by core rust-libp2p maintainers. Server & client modules; constants: `DEFAULT_TTL`=2 h, `MIN_TTL`=2 h, `MAX_TTL`=72 h, `MAX_NAMESPACE`. {crates.io/crates/libp2p-rendezvous + deps.dev + libp2p.github.io/rust-libp2p docs, high, health}
- **go-libp2p**: rendezvous lives in a separate repo `libp2p/go-libp2p-rendezvous`, described by a maintainer (2021) as "a prototype… a bit behind the spec"; effectively stale (a 2026 community fork exists). **js-libp2p**: `js-libp2p-rendezvous` repo self-describes as WIP. {github.com/libp2p/go-libp2p-rendezvous + discuss.libp2p.io/t/general-rendezvous-server/884 + github.com/libp2p/js-libp2p-rendezvous, high, health}
- **Precedent for private rendezvous**: a third-party deployment (Lattice) runs rust-libp2p rendezvous in "private mode" with an `allowed_peer_ids` allowlist and rejects namespace-less enumeration — confirming restriction to known peers is done **outside** the protocol, at connection level. {latticepm.net/docs/services/rendezvous, medium, pattern}
- **Assessment for our requirements**: rendezvous fits the "records only on direct contacts" topology naturally (every device runs a point serving only its contacts; allowlist = contact list). But: signed peer records are **cleartext multiaddrs** (no per-recipient encryption in spec), identifiers are PeerIDs not rotating opaque keys, and the discoverer must **already be able to reach** the rendezvous point — it cannot help when a contact's address changed. {synthesis of above, high, assessment}

### Claims — Tox

- **DHT mechanics**: Kademlia over **UDP only**; every node has an **ephemeral DHT keypair renewed each restart** (node address = DHT pubkey). Nodes keep Close/Search lists; `get_nodes`/`send_nodes` return up to 4 packed nodes (ip+port+pubkey, 32-byte PK). Friend's DHT pubkey is found via the **onion module** (3-hop announce paths hiding the announcer's IP); once known, DHT finds the friend's IP and connects directly, using UDP hole punching if needed. {toktok.ltd/spec + github.com/TokTok/c-toxcore DHT.c, high, spec}
- **Bootstrap**: "Joining a Tox network requires connecting to a well-known node called a bootstrap node. Anyone can run a bootstrap node" — dedicated `tox-bootstrapd` daemon exists; wiki maintains a list of public bootstrap nodes (run by community, must have static IP/port/pubkey). **However** clients save known nodes and can re-bootstrap from them (`dht_connect_after_load`), so bootstrap servers are a first-run convenience, not a permanent server dependency. {wiki.tox.chat/users/nodes + toktok.ltd/spec + tox-bootstrapd.conf, high, spec}
- **c-toxcore health: ACTIVE** — v0.2.24 released 2026-11-01, v0.2.23 2026-06-03 (fixed a critical advisory); commits through Oct 2026 by iphydf/Green-Sky. {github.com/TokTok/c-toxcore commits + CHANGELOG.md, high, health}
- **tox-rs: DEAD** — last release v0.2.0 (2022-12-10), last commit ~3 years ago; OpenSSF "Maintained 0/10, 0 commits and 0 issue activity in last 90 days"; OpenHub labels it Inactive ("maintained by nobody", 0 commits in 12 months). GPLv3. TokTok states a *new* Rust implementation "is in progress" evolving with the spec model — separate from tox-rs; also warns **neither protocol nor implementation has undergone peer review** and Tox is not recommended where proven security is required. {repositorystats.com/tox-rs/tox + openhub.net/p/tox-rs + deps.dev + toktok.ltd, high, health}
- **Rust reusability**: poor today — usable path would be FFI to C c-toxcore (`rstox` bindings exist, stale) or the unfinished new impl. {synthesis, medium, health}
- **License**: c-toxcore GPLv3; tox-rs GPLv3 — GPL on a library may matter for the app's own licensing model (Enola license) — flag for decision. {repo license fields, high, health}

### Claims — OpenDHT / Jami

- **Model**: Kademlia (not Mainline-compatible), 160-bit keys, values up to 64 KiB, values distributed with redundancy to nodes near the key; every node can read/write; per-value "value types" control expiry/edit policy. {github.com/savoirfairelinux/opendht + wiki API-Overview, high, spec}
- **Crypto layer**: `SecureDht` adds optional signed and **encrypted values** (GnuTLS certs; certs themselves published on the DHT). `putEncrypted(key, contact_id, value)` encrypts to a recipient cert; encrypted values are always signed with the signature inside the ciphertext (hides signer in transit) but **cannot be edited** since storage nodes can't verify authorship. {wiki API-Overview + blog.savoirfairelinux.com 2015 + repo AGENTS.md, high, spec}
- **Caveat**: DHT **transport protocol itself is unencrypted** (as of Nov 2023 issue; maintainer: "we are investigating adding encryption at the protocol level"). Storage nodes learn: key (infohash), ciphertext blob, timing, and that *someone* queried that key — i.e. keys must be opaque for privacy, which matches our keyed-identifier requirement. {github.com/savoirfairelinux/opendht/issues/407, medium-high, spec}
- **Bootstrap**: Jami defaults to `bootstrap.jami.net:4222` (Savoir-faire Linux-run) on the public network ID 0, but any node can bootstrap; clients keep a **persistent node cache** so bootstrap is needed only for first join or if cached nodes are dead. `dhtnode` standalone nodes get added to the default bootstrap list on request. Same pattern as Tox: no permanent server, but first contact required. {docs.jami.net distributed-network + lan-only + jami.net/why-is-jami-truly-distributed, high, spec}
- **Health: ACTIVE** — v4.4.1 Sep 2026, commits through Sep 2026 (aberaud). **License: MIT** since v3.7.1 (was GPL before — important change). {repo commits/releases + LICENSE, high, health}
- **Rust path**: **official `opendht` crate v4.4.104 on crates.io** (MIT, by Jami devs) — safe API, `async` streams, `serde` typed records — but it **links the native `libopendht-c` C library, not bundled**: needs system-installed OpenDHT or manual LIBRARY_PATH setup. Not pure-Rust; adds a C++/GnuTLS dependency chain. {docs.rs/crate/opendht/latest + BUILD.md + issue #741, high, health}

### Claims — generic Kademlia

- **Bootstrap-free DHT does not exist**: joining requires ≥1 already-connected node — "bootstrap nodes… are not special in any way other than being listed in some predefined list"; they're just the first contact, and the standard mitigation is caching stable nodes between sessions (exactly what Tox/Jami do). No well-known DHT found that works with zero known peers over WAN. {delta1.github.io/tari-university DHT report, high, spec}
- **Sybil**: vanilla Kademlia has **no Sybil resistance** — attackers can mint unlimited IDs *and choose their position* in keyspace; defenses in literature rely on strong identity or central authority (both out for us). {giulianomega.com S/Kademlia + INRIA hal-00786438, high, spec}
- **Eclipse**: feasible esp. where k-buckets are underpopulated (small/sparse networks stay vulnerable longer); cheap when many peers can share one IP. Kademlia's bucket-update rule gives partial resilience only at critical mass. {same two sources, high, spec}
- **Mostly-non-collaborating DHT**: a DHT's routing *is* the collaboration — nodes that only serve their own contacts and refuse to route/store for others effectively don't form a DHT (no shared routing table, no keyspace coverage). The requirement "records ONLY on direct contacts" is therefore **architecturally incompatible with using DHT storage**; a DHT could only serve as a reachability overlay, but lookups still leak the queried key to every intermediate node and still need a first contact. {synthesis from Tari + Kademlia mechanics, high, assessment}

### Decision-relevant synthesis

- **Both candidates hit the same cold-start wall**: rendezvous needs a reachable point; DHT needs ≥1 known node. Node caches soften but never eliminate it — this is inherent to "no servers," not a flaw of one candidate.
- **Rendezvous maps cleanly onto the mandated topology** (contacts-as-points) and is the only candidate with a maintained pure-Rust implementation — but per-recipient encryption, rotating identifiers, and contact-only auth must all be layered on top (auth wrapper + per-recipient namespaces + custom record payload — at which point it's a custom protocol using the crate's stream plumbing).
- **All three DHTs as designed are eliminated by "records only on direct contacts"**: they require storing/announcing on stranger nodes. OpenDHT's `putEncrypted` is the closest fit conceptually (encrypted-to-recipient values, opaque key possible) but still requires strangers to custody ciphertext and the routing overlay itself.
- **The live question for round 2**: whether endpoints can be exchanged *peer-to-peer through the contact graph* (a contact-of-contact introducer pattern) or whether the design accepts a small set of voluntary "rendezvous/custody" nodes — both preserve "no servers" better than any public DHT.

### Leads worth chasing

- rust-libp2p `libp2p-rendezvous` server internals — whether records can carry an opaque payload instead of a standard signed peer record, and how hard the auth-wrapper pattern is (discussion #5638 has maintainer pointers).
- Whether the project's real requirement could be met by **direct peer records exchange over Noise-secured streams to contacts only** (rendezvous-shaped but contact-scoped) — i.e., skip the discovery protocol entirely.
- TokTok's *new* Rust implementation (separate from dead tox-rs) — worth locating its repo/maturity before dismissing.
- `opendht` crate viability if a private friend-graph DHT is ever reconsidered — the encrypted-value + opaque-key model is the best fit among DHTs.
