## Digest: Briar BRP + bilateral rendezvous (r1)
_Subagent: 7a8ca2b4 · Round 1 · accessed 2026-11-13_

### Claims — Briar BRP

- **BRP v0 derivation chain (spec)**: `raw_secret = X25519 DH(pri_self, pub_peer)` → `static_master_key = HASH("org.briarproject.bramble.transport/STATIC_MASTER_KEY", raw_secret, pub_a, pub_b)` → `rendezvous_key = KDF(static_master_key, "...rendezvous/RENDEZVOUS_KEY", int_8(version=0))` → per-transport `stream_key = KDF(rendezvous_key, "...rendezvous/KEY_MATERIAL", transport_id)`. Primitives: BLAKE2b hash, keyed-BLAKE2b MAC, Salsa20 stream, X25519. — source: `code.briarproject.org/briar/briar-spec/-/blob/master/protocols/BRP.md` (Briar Project, spec committed 2019-09-30, accessed 2026-11-13; confidence: high; class: spec).
- **Only transport in BRP v0 is a derived Tor v3 onion service** (`"org.briarproject.bramble.tor"`): `key_material = STREAM(stream_key, 64)`; bytes 0–31 = Alice's Ed25519 seed, 32–63 = Bob's; each seed is the master identity key of a hidden service (per Tor Rendezvous Spec v3 §1.9, address per §6). **Each peer publishes its own derived onion AND dials the peer's** — the pair's contact details are computed, never transmitted. — same source; confidence: high; class: spec.
- **Polling/availability window**: each peer keeps endpoints open and dials the other once per minute for up to **48 hours** after key exchange; on failure the rendezvous must be manually restarted by both. Requires overlapping online presence within the window (Tor HS intro points absorb the rest — both need not be simultaneously online, only within the same window). — same source (commit d5d6e2a3); confidence: high; class: spec.
- **BRP does not authenticate the remote peer**; it returns connections plus the `static_master_key` to the app layer for key derivation. — same source §2.4; confidence: high; class: spec.
- **Adversary model**: adversary knows both public keys but not private keys; see-only adversary cannot compute endpoints (they're behind the DH secret) — so **no endpoint records are deposited anywhere except Tor's own HSDirs**, which store only blinded, encrypted descriptors unlinkable to the pair. MITM possible only if the key exchange channel is modifiable. — same source §1.2; confidence: high; class: spec.
- **BRP has NO rotation**: the pair's onion addresses are static for the rendezvous (single use, at contact setup). Rotation is not part of v0. — inferred from spec (rendezvous_key has no time/epoch input); confidence: high; class: spec.
- **Briar project health**: officially in **maintenance mode** since 2026-07-09 (essential security updates/bugfixes only; a 2025 shutdown decision was reversed after community response). Releases continue: 1.5.24 dated 2026-10-30, tags through release-1.5.22 (Oct 2026). — `briarproject.org/news/2026-maintenance-mode/` + `code.briarproject.org/briar/briar/-/tags`; confidence: high; class: health.
- **Licensing**: Briar core/Android = **GPLv3-only**; Briar Desktop = **AGPLv3** (confirmed relicensing discussion exists). — `code.briarproject.org/briar/briar/-/blob/master/LICENSE.txt`, briar-desktop issue #185; confidence: high; class: health.

### Claims — Bilateral patterns

- **Cwtch (Open Privacy)** = mailbox-on-own-onion: every profile runs a v3 onion service; P2P chat requires both peers online; auth via Ricochet `im.ricochet.auth.hidden-service` channel then ephemeral session keys (offline-deniable). Identifier embeds the onion address → **anyone holding the identifier can probe/track online status** (static, non-rotating). Servers exist only as opt-in untrusted group/offline infrastructure. **Actively maintained**: lib v0.30.0 (2025-08-26), UI v1.16.3 (2025-10-31). Go; reusable pieces in `git.openprivacy.ca` (Tapir, connectivity). — cwtch.im/cwtch.pdf; docs.cwtch.im; git.openprivacy.ca/cwtch.im/cwtch(-ui)/releases; confidence: high; class: health.
- **Ricochet-Refresh** = pure ancestor pattern: contact address `ricochet-v3://{service-id}` — identifier IS the onion endpoint. Actively maintained (v3.0.47, 2026-10-21; Blueprint for Free Speech; tor 0.4.9.x, vanguards-lite). — github.com/blueprint-freespeech/ricochet-refresh/releases; ricochetrefresh.net; confidence: high; class: health.
- **Quiet** = per-member onion service + community member list synced via OrbitDB CRDT over Tor; joining requires an online community owner; all rendezvous is "dial known member onion". Very active (11.3.1, 2026-10-28) **but drifting toward optional infra** (QSS "Quiet Storage Service", push notifications in changelog). Bilateral-capable but group-oriented; member onions are visible to the whole community. — github.com/TryQuiet/quiet wiki + releases; braid.org/meeting-16.1; confidence: high; class: health.
- **Jami** = NOT bilateral: presence/endpoint records (`DeviceAnnouncement`) are stored on **OpenDHT** under the hash of the device cert (TTL ~10 min), i.e., on arbitrary third-party DHT nodes; contact lookup → call request carrying ICE candidates → ICE/TLS or DTLS. Mechanically proves a rendezvous channel CAN carry ICE endpoint records for coordinated UDP punching — but violates "records only on direct contacts" (global DHT) and leaks presence to DHT observers. Optional OpenDHT proxy + push for mobile. — docs.jami.net contact-management/calls/faq; jami.net/jami-and-proxys; confidence: high; class: spec.
- **Keet/Hyperswarm (Holepunch)** = NOT bilateral: `announce`/`lookup` of signed records under 32-byte topics on HyperDHT; hole punching is coordinated via the DHT nodes themselves; optional `blind-relay` relay fallback exists. Topic-as-opaque-keyed-identifier is the interesting idea; the storage location (global DHT) is not. — github.com/holepunchto/hyperdht + /hyperswarm; docs.pears.com; confidence: high; class: spec.
- **Time-rotated derived onion — prior art exists**: `meshtor/src/rotate.rs` implements `onion_addr = f(32-byte seed, floor(clock/86400))` — every member computes the same rotating address offline, no directory; documents the limits (no revocation, no forward secrecy, descriptor propagation sets a floor on period). — `0rcus.vercel.app/git/r/meshtor/files/src/rotate.rs` (small project, treat as idea-evidence not production); confidence: medium; class: pattern.
- **Tor v3 already rotates the *visible* identifier daily**: HSDir upload locations and blinded descriptor keys change every `hsdir-interval` (default 1440 min) via time periods + shared random value — so even a *static* pair-derived onion presents rotating blinded keys to directories/observers. — torproject.gitlab.io/torspec/rend-spec-v3.html; confidence: high; class: spec.
- **Operational onion-rotation prior art on Briar's own stack**: Zerion fork of `onionwrapper` rotates v3 onions every 5–14 days, running old+new services concurrently during migration — a template for rotating per-contact onions without losing reachability. — github.com/zerionproject/Zerion docs/wire/B4_ONIONWRAPPER_API.md; confidence: medium (self-reported, unverified code); class: pattern.
- **Academic/engineering lineage**: 2018 tor-dev thread "Temporary hidden services" describes the shared-secret-derived-onion approach (BRP ancestry); Höller et al., WTMC 2021, "Feasibility of Short-Lived Dynamic Onion Services" — formal treatment of time-derived onion lifetimes. — archive.torproject.org tor-dev 2018-10; mroland.at PDF; confidence: high for existence; class: academic.

### Fit assessment vs. hard requirements (assessment, not decision)

- **BRP trivially satisfies "records only on direct contacts"** because it deposits *no endpoint records at all* — endpoints are derived from the pair DH secret; the only artifacts are Tor HS descriptors on Tor's own (already-approved) infrastructure, encrypted and daily-blinded by Tor itself.
- **BRP gives you the rendezvous channel for endpoint exchange**: the rendezvous connection carries whatever the app sends over it (Briar exchanges transport contact info there). For this design, that channel could carry UDP-hole-punch coordination data. Caveat: BRP's own channel is Tor (TCP-over-onion); UDP punching would happen *after* the rendezvous, using endpoints exchanged on it.
- **Gaps in BRP for the requirements**: (a) **no rotation** of pair identifiers — extension is straightforward (add epoch to the stream_key KDF, à la meshtor/Zerion) but is a spec change; (b) **48h one-shot semantics** — continuous availability requires repeating/refreshing rendezvous, which the rotation extension also provides; (c) **requires running Tor onion services per contact pair** (Briar does exactly this; cost = one HS publish + connect per contact).
- **Pattern ranking for bilateral-only operation**: derived-endpoint (BRP) > static mailbox-on-own-onion (Cwtch/Ricochet/Quiet — simplest, but identifier is probeable & non-rotating) >> DHT-topic (Jami/Keet — disqualified by "contacts-only" storage). No examined project implements consistent/rendezvous-hashing among mutual contacts or pull-polling with opaque rotating tokens as named mechanisms.
