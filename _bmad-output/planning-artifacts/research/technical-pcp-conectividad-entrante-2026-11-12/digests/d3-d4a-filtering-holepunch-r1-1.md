## D3 — Is deny-inbound the real default? Answer: mostly yes for mainstream CPE, but ~20–25% of residential IPv6 is *unfiltered*, and mobile carriers commonly filter inbound *in the network*.

**C1 — RFC 6092's reference model is deny-inbound + stateful return path.**
- {claim: "The general operating principle is that transport layer traffic is not forwarded into the interior network of a residential IPv6 gateway unless it has been solicited explicitly by interior transport endpoints, e.g., by matching the reverse path for previously forwarded outbound traffic, or by matching configured exceptions… All other traffic is expected to be discarded or rejected." Default mode also *permits* IPsec/IKE/HIP inbound and *denies* inbound tunnel initiations (RFC 2473-style).", URL: https://www.rfc-editor.org/rfc/rfc6092.html, publisher: IETF/RFC Editor, pub_date: 2011-01, accessed: 2026-11-12, confidence: high, class: primary spec}
- {claim: "RFC 6092 §3.2.3 defines UDP stateful filtering modeled on RFC 4787: outbound UDP creates a 5-tuple state record (interior+exterior addr/port); REC-14: state MUST NOT expire before 2 min idle, default 5 min; REC-15 allows shorter for well-known ports. So 'outbound opens return path' and 'keepalives needed every <2min' are *specified behavior*, not folklore.", URL: https://www.rfc-editor.org/rfc/rfc6092.html, publisher: IETF, pub_date: 2011-01, accessed: 2026-11-12, confidence: high, class: primary spec}
- Caveat: RFC 6092 is Informational — a recommendation to CPE makers, not a mandate. The measured literature below shows actual CPE behavior diverges both directions.

## D4a — Can coordinated traversal defeat IPv6 filtering without infrastructure?

**D1 — Yes: on RFC 6092-style stateful firewalls, coordinated mutual UDP send works — and it is *tested*, not just theorized.**
- {claim: "Mechanism per spec: outbound UDP creates a 5-tuple filter record; inbound from that exterior endpoint is then admitted (RFC 6092 §3.2.3). Since IPv6 does no port translation, an IPv6 stateful firewall behaves equivalently to a port-restricted-cone NAT for traversal purposes — no port-prediction needed.", URL: https://www.rfc-editor.org/rfc/rfc6092.html, publisher: IETF, pub_date: 2011-01, accessed: 2026-11-12, confidence: high, class: spec-derived}
- {claim: "Practitioner test: 'Decent stateful firewalls match on the full 5-tuple, functionally equivalent to symmetric NAT but without port rewriting — equivalent to port-restricted cone NAT.' PCAPs of popular IPv6 P2P apps (VoIP/video) showed direct peer src/dst addresses (ruling out relays) through stateful firewalls.", URL: https://blog.ipspace.net/2025/04/response-peer-to-peer-apps-ipv6/, publisher: ipSpace.net (reader response w/ lab tests), pub_date: 2025-04, accessed: 2026-11-12, confidence: med-high, class: measured/tested account}
- {claim: "Tracked-issue test (EasyTier #778): both peers behind IPv6 firewalls with inbound prohibited and address+port-dependent filtering; mutual sends from port 7777 to peer's 7777 → both received and session established. Author notes IPv6 'symmetric UDP firewall' filtering is *easier* to traverse than symmetric NAT since no port guessing.", URL: https://github.com/EasyTier/EasyTier/issues/778, publisher: GitHub issue, pub_date: ~2025, accessed: 2026-11-12, confidence: med-high, class: tested account}
- {claim: "Production account: Tailscale treats IPv6 endpoints as 'easy NAT — direct connections in almost every situation'; prefers native IPv6 direct paths when both peers have them.", URL: https://tailscale.com/docs/reference/device-connectivity and https://tailscale.com/blog/nat-traversal-improvements-pt-1, publisher: Tailscale, pub_date: docs current / blog ~2024-25, accessed: 2026-11-12, confidence: high, class: production account}
- {claim: "Theoretical basis + terminology: RFC 5128 documents UDP hole punching and TCP 'simultaneous open' through NATs; success depends on endpoint-(in)dependent filtering, and *both* ends must send. For IPv6 stateful firewalls the same model applies minus address translation.", URL: https://www.rfc-editor.org/info/rfc5128/, publisher: IETF, pub_date: 2008-03, accessed: 2026-11-12, confidence: high, class: primary spec/historical}
- Timing note: "simultaneous" send doesn't need precise simultaneity — each side only needs to have sent once for the other's packets to match state; first packets get dropped, retries succeed (mechanism described for NATs at https://networks.jelia.nyc/nat-traversal/, secondary explainer; consistent with RFC 6092 state semantics). Strict simultaneity is unnecessary — sequential mutual sends work; what fails is *one-way-only* initiation toward a filtering peer.

BUT IPv6 success measured *lower* than IPv4 — cause unresolved (measurement artifact vs. inherent).", URL: https://github.com/probe-lab/network-measurements/blob/main/results/rfm15-nat-hole-punching.md and https://github.com/libp2p/go-libp2p/issues/2068, publisher: ProbeLab/libp2p, pub_date: 2022–2023, accessed: 2026-11-12, confidence: med-high, class: measured study — note the IPv6 shortfall is unexplained}
- {claim: "Historical IPv4 in-the-wild: >80% of hole-punch attempts between punchable peers succeeded (BitTorrent measurement, 15,545 connections).", URL: https://opendl.ifip-tc6.org/db/conf/networking/networking2011-2/HalkesP11.pdf, publisher: IFIP Networking 2011 (Halkes & Pouwelse), pub_date: 2011, accessed: 2026-11-12, confidence: med (historical), class: measured study}

**D3-failure-modes — when coordinated punching does NOT work:**
- Stateless/ACL-based carrier filtering that blocks *all* inbound to the subscriber prefix regardless of flow state (mechanism acknowledged on NANOG; consistent with EE's "block applied in core network"). Whether such filters create per-flow UDP return state is unverified per-carrier — this determines whether cellular punching works at all.
- {claim: "Counter-anecdote: developer reported IPv6 UDP hole punching failing between a Wi-Fi host and an iOS device on IPv6 cellular — both sent packets, neither received (works on same Wi-Fi).", URL: https://stackoverflow.com/questions/43686011/, publisher: StackOverflow, pub_date: ~2017, accessed: 2026-11-12, confidence: low-med, class: anecdote}
- {claim: "Paranoid CPE policies can block categories regardless of state — e.g., Xfinity 'Medium' blocks P2P applications, 'High' blocks nearly everything.", URL: https://routersnetwork.net/blog/setup-firewall-xfinity-gateway/, accessed: 2026-11-12, confidence: med, class: secondary doc}
- {claim: "Ironically, *no* filtering also means punching is trivially unnecessary — inbound just works (25% of measured IPv6 end-host networks, per C3).", source: CCS 2026 paper above, confidence: high}

**D4 — The rendezvous crux (decision-relevant).**
- No source contradicts this: **the traversal mechanism itself needs no server** — peers' external endpoint = their own global IPv6 address:port (no STUN needed; nothing to discover but your own address). What *cannot* be eliminated is learning the peer's address:port — with literally zero shared signaling channel, two peers can never name each other. With *any* out-of-band exchange (QR, user paste, existing app channel, bootstrap peer), direct UDP succeeds wherever both firewalls are stateful-per-outbound (RFC 6092 model), which evidence suggests is the majority but far from all of residential IPv6, and where the carrier doesn't drop mobile-terminated traffic outright.
- Non-punching ways to open a path (for completeness): manual port sharing (AVM docs), UPnP WANIPv6FirewallControl pinholes (official UPnP SDCP spec, https://upnp.org/specs/gw/UPnP-gw-WANIPv6FirewallControl-v1-Service.pdf, 2010-12 — but UPnP IPv6 support is 'not the case for all IPv6 routers' per https://www.techtarget.com/news/Ensuring-P2P-apps-dont-cause-network-performance-issues-with-IPv6/867705/), and PCP (RFC 6887) IPv6 pinholes — NetBird merged PCP with IPv6 pinhole support Jan 2026 (https://github.com/netbirdio/netbird/pull/5219), indicating real-world uptake, though CPE support remains uncommon.

## Contradictions reported
1. **Does IPv6 punching work reliably?** EasyTier test + ipSpace PCAPs + Tailscale production all say yes on stateful firewalls; libp2p's measured campaign found IPv6 success *lower* than IPv4 (unexplained); one SO anecdote of total failure on cellular. Best synthesis: works on RFC 6092-type CPE stateful filters; carrier-side filtering behavior varies and may not admit return-flow state.
2. **Is deny-inbound "the" default?** RFC 6092 + OpenWrt + AVM + Xfinity say yes for mainstream gear; measured studies say ~20–25% of residential IPv6 is entirely unfiltered (2/10, 5/25, 25% of networks, 14.9M reachable internal hosts). Both true: the app cannot assume either.
3. **Comcast**: official "we don't block" vs. a Business-gateway model whose IPv6 firewall was non-functional (inbound open by default) — CPE inconsistency, not carrier policy.

- Broad survey of **enterprise/public Wi-Fi IPv6 inbound policy** — only per-institution examples (Northwestern, LMU).
